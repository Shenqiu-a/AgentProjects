# 微服务拆分与启动

## 1. 这次改了什么

原 backend 是一个 Spring Boot 应用，目前真正完成的业务主要是认证。现在 backend/pom.xml 是聚合父工程，每个服务都有自己的启动类、依赖、配置、迁移和可执行 JAR。服务之间不引用其他服务的 Maven 模块，也不查询对方的数据库。

~~~mermaid
flowchart LR
    Browser[Vue 前端] --> Gateway[Nginx 网关 :8080]
    Gateway --> Auth[auth-service :8081]
    Gateway --> Order[order-service :8082]
    Gateway --> Knowledge[knowledge-service :8083]
    Gateway --> Agent[agent-service :8084]
    Order -->|会话与 CSRF 核验| Auth
    Knowledge -->|会话与 CSRF 核验| Auth
    Agent -->|会话与 CSRF 核验| Auth
    Auth --> AuthDB[(认证库)]
    Auth --> Redis[(Redis)]
    Order --> OrderDB[(订单库)]
    Knowledge --> KnowledgeDB[(知识库)]
    Agent --> AgentDB[(Agent 库)]
~~~

没有引入注册中心和消息队列；Compose DNS 提供固定服务名。之后需要异步事件时再增加消息中间件和 outbox，不以空配置宣称已经具备分布式事务。

## 2. 文件从哪里看

| 位置 | 职责 |
|---|---|
| backend/pom.xml | 聚合构建、Java/Boot/AI 版本管理 |
| backend/service-common | 响应封装、Caller、远程鉴权过滤器、安全配置；不放业务实体或 Repository |
| backend/auth-service | 原登录模块、账号 Repository、Redis Session/限流、内部身份接口 |
| backend/order-service | 订单数据库与只读订单入口 |
| backend/knowledge-service | 知识数据库、PDF 依赖、管理员文档目录 |
| backend/agent-service | Agent/工单数据库、Spring AI 依赖、本人工单读取入口 |
| backend/legacy-db/migration | 原单体 V1—V5，保留内容与历史校验值 |
| compose.yaml | 完整新栈；独立项目名和数据卷 |
| deploy/microservices | 多阶段镜像构建与网关路由 |
| scripts/Start-Microservices.ps1 | 构建、启动与逐服务健康等待 |
| scripts/MicroserviceDataMigration.java | 本地旧库只读快照、空目标复制、演示账号初始化 |

auth-service 的启动类沿用 AfterSalesAgentApplication 名称。它只扫描 security/common，避免误装载业务服务的远程鉴权配置。其他三个启动类显式导入 ServiceSecurityConfiguration。

## 3. 18 张表的归属

| 服务 | 数据库 | 表 |
|---|---|---|
| auth | after_sales_auth | app_user |
| order | after_sales_order | product、policy_rule、customer_order |
| knowledge | after_sales_knowledge | knowledge_document、document_ingestion、knowledge_chunk |
| agent | after_sales_agent | conversation、chat_message、agent_run、tool_call、run_event、confirmation、ticket、ticket_status_history、idempotency_record、evaluation_job、evaluation_case_result |

新数据库保留各服务内部的外键、状态检查、唯一索引和向量维度约束。跨服务的 user_id、order_id、product_id、policy_rule_id 只保留标识，不能建立跨库外键；新增写接口时必须通过所属服务校验身份、归属和资源状态。

确认单与工单存在双向引用以及“确认只创建一张工单”的事务要求，因此同属 Agent 服务。本次没有把它们继续拆成两个写服务。后续确认创建时，订单读取与本地提交之间仍有跨服务并发问题，需要定义版本校验、预留或事件补偿协议，不能直接照搬旧单库锁订单的流程。

评测表暂由 Agent 管理；真正运行评测时仍应部署独立评测栈。没有实现评测执行器。

每个服务的新 V1 只用于新库。绝不能将 AUTH/ORDER/KNOWLEDGE/AGENT_DATABASE_URL 指向旧 after_sales 或旧 after_sales_eval，并通过 baseline 绕过校验。

## 4. 一个请求如何执行

1. 浏览器经过前端同源代理访问 /api/v1/auth/csrf、login、me、logout；Nginx 转给 auth-service。
2. 认证服务继续使用 BCrypt、Cookie Session、Redis、CSRF 和原登录限流。
3. 浏览器请求订单等业务接口时，业务服务拿 Cookie 请求 auth-service 的 /internal/auth/identity，并附内部 SERVICE_AUTH_TOKEN。
4. 读请求使用内部 GET；POST/PUT/PATCH/DELETE 等写请求使用内部 POST，同时转发 X-CSRF-TOKEN，让认证服务原来的 CSRF 过滤器检查同一会话。
5. 认证服务重新查询启用状态，返回用户 UUID/角色。业务服务建立本次请求的 SecurityContext，并在 SQL 中使用该 UUID 限制归属。
6. 内部请求连接超时 2 秒、整体超时 3 秒。认证故障返回 503，失效会话返回 401，CSRF/权限失败返回 403，不继续执行业务。

业务服务不读取 Redis Session，也不接受浏览器自报的 X-User-Id/X-User-Role。服务端配置的内部 token 会覆盖浏览器同名头。网关不代理 /internal，Compose 不发布四个 Java 服务端口；本地 IDE 模式只绑定回环地址。

当前这种同步鉴权容易学习和排查，但认证服务会成为公共依赖。今后有吞吐需求再考虑短期签名令牌或专门的身份协议。生产环境还需要 HTTPS、Secret 管理、服务间 TLS 与备份策略；当前 Compose 是本机开发栈。

实现参考：[Spring Security 过滤器链](https://docs.spring.io/spring-security/reference/servlet/architecture.html) 与 [CSRF 机制](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

## 5. Docker 启动

从 after-sales-agent 目录执行：

~~~powershell
.\scripts\Initialize-MicroserviceEnvironment.ps1
.\scripts\Start-Microservices.ps1
~~~

首次构建需要下载镜像和 Maven 依赖。使用 .env.microservices 独立配置，服务 token 与各数据库/Redis 密码随机生成。脚本不会覆盖已有配置。

数据库只发布本机端口：认证 55431、订单 55432、知识 55433、Agent 55434；Redis 为 56379。网关为 8080，可在 .env.microservices 设置 GATEWAY_PORT。

~~~powershell
docker compose --env-file .env.microservices ps
docker compose --env-file .env.microservices logs --tail 100 auth-service
Invoke-RestMethod http://127.0.0.1:8080/health/orders
~~~

只启动基础设施：scripts/Start-Microservices.ps1 -InfrastructureOnly。认证多实例：scripts/Start-Microservices.ps1 -AuthReplicas 3。Session 和登录限流仍共享 Redis。

停止栈使用 docker compose --env-file .env.microservices down；日常停止不要加 -v，因为它会删除新库数据卷。

原 Portainer 管理栈 compose.portainer.yaml 独立保留。旧 Start-ManagedDeployment.ps1 现在只是新启动脚本的兼容入口，不再自动创建旧单体 Portainer Stack；需要管理新栈时在 Portainer 中导入当前 Compose 并配置变量及挂载路径。

## 6. 旧数据如何迁移

复制是显式动作。当前开发数据没有被自动迁移或重置，旧库仍由旧 .env 描述。

1. 启动新栈，让四个服务各自创建新库表结构。
2. 保留旧 .env 的 DATABASE_URL、DATABASE_USERNAME、DATABASE_PASSWORD。DATABASE_URL 必须明确指向本机 after_sales。
3. 先查看数量：

~~~powershell
.\scripts\Migrate-MicroserviceData.ps1 -Action plan
~~~

4. 确认目标业务表全部为空后执行：

~~~powershell
.\scripts\Migrate-MicroserviceData.ps1 -Action copy
~~~

工具复制所有 18 张表，保留 UUID、BCrypt、状态、JSON 和向量值。源连接只读并使用可重复读快照；每个目标使用本地事务，在提交前检查延迟外键。它不复制旧 Flyway 历史，因为新服务拥有独立的迁移链。

这不是在线迁移工具：迁移期间不要写新库。四个目标依次提交，没有两阶段提交；若在提交阶段中断，工具会打印已经 COMMITTED 的服务，需检查并使用新的空目标重试，不能假设跨库全部回滚。工具不会清空、覆盖或静默合并现有数据。

复制账号后继续使用原 data/local/test-accounts.properties 的密码。真实上传文件还需单独备份、迁入知识服务上传卷并核对 storage_key；行复制不包含文件，也不会把 mock 向量转换成真实 Embedding。

如果不沿用旧数据，只创建新库演示账号：

~~~powershell
.\scripts\Migrate-MicroserviceData.ps1 -Action seed-accounts
~~~

密码写在 data/local/microservice-accounts.properties，仅本机查看。重复执行不改已有账号密码。此操作不生成订单、知识或工单样例；空库列表返回空数组。seed-accounts 与整库 copy 是两条初始化路径，不能先 seed 再向非空目标 copy。

原 scripts/Initialize-Database.ps1 继续管理旧 after_sales，已改为读取 legacy-db 迁移；它不会初始化微服务数据库。

## 7. 在 IDEA 或终端逐个启动

先启动新基础设施，然后构建：

~~~powershell
.\scripts\Start-Microservices.ps1 -InfrastructureOnly
mvn -B -ntp -f backend/pom.xml install -DskipTests
~~~

IDEA 导入 backend/pom.xml，分别运行四个 Application，Working directory 设为各模块目录。配置从 ../../.env.microservices 加载。端口分别为 8081—8084。

终端也可以从项目根目录的四个窗口分别启动：

~~~powershell
java -jar backend/auth-service/target/auth-service-0.0.1-SNAPSHOT.jar
java -jar backend/order-service/target/order-service-0.0.1-SNAPSHOT.jar
java -jar backend/knowledge-service/target/knowledge-service-0.0.1-SNAPSHOT.jar
java -jar backend/agent-service/target/agent-service-0.0.1-SNAPSHOT.jar
~~~

前端复制 frontend/.env.example 到 frontend/.env.local，设置 MICROSERVICES_DIRECT=true；Vite 会按路径转到四个本地进程。通过网关联调时设置为 false，并使用 BACKEND_URL。修改配置后重启 Vite。

backend 现在是父工程，直接在这里运行 spring-boot:run 不再代表一个应用。开发单个模块时先 install 共享模块，再使用 mvn -f backend/order-service/pom.xml spring-boot:run。

## 8. 本次提供的接口范围

| 服务 | 已实现的入口 |
|---|---|
| auth | 原四个认证接口；内部 GET/POST /internal/auth/identity |
| order | GET /api/v1/orders；GET /api/v1/orders/{orderId} |
| knowledge | 管理员 GET /api/v1/knowledge/documents |
| agent | GET /api/v1/tickets/{ticketId} |
| gateway | /gateway-healthz；/health/auth、orders、knowledge、agent |

新增业务读取接口目前返回数据库事实的基础视图，列表使用 offset/limit（limit 1—100）。原 after-sales-agent-spec/openapi.json 是完整产品目标契约；售后资格、完整订单 DTO、工单状态历史和其中其他操作仍未实现，不能当作已经通过该契约验收。

未登录请求返回 401；其他客户的订单/工单返回 404；普通客户访问知识目录返回 403。前端当前仍只接入登录，业务页面不在本次拆分范围内。

模型、RAG、SSE 执行、上传解析、确认创建工单和真实评测 worker 都没有在此次拆分中补齐，依赖或配置项存在不代表功能运行。
