# 登录限流与多实例部署

后端使用 Redis 滑动窗口限流，并通过 Spring Session Redis 共享登录身份和 CSRF 状态。Java 21、Spring Boot 4.0.8、Spring Security 7；开发 Redis 镜像固定为 7.4.12。这里的多实例指登录后端，不包括尚未实现的 Agent worker/文档存储集群化。

## 请求流程与规则

请求先经过 Spring Security 的 CSRF 校验和 MVC 参数校验，然后在 AuthController.login 中依次检查 IP、IP＋账号、账号三个共享额度，全部通过后才查询账号、校验 BCrypt 密码、更新 Session ID 并保存 SecurityContext。

| 规则 | 默认额度 | 目的 |
|---|---|---|
| IP | 60 秒 30 次 | 限制同一来源批量尝试 |
| IP＋账号 | 300 秒 5 次 | 限制同一来源反复尝试同一账号 |
| 账号 | 300 秒 20 次 | 限制换 IP 继续尝试 |

统计的是登录尝试，成功也占额度，成功后不清空。账号不存在、密码错误、禁用账号均使用相同规则。用户名不独立 trim/转小写，以匹配当前 PostgreSQL 的 username 精确查询；以后变更账号匹配规则时要同步调整限流标识。

每个维度使用一个 Redis Sorted Set，以 Redis TIME 为统一时钟、UUID 为请求标识。Lua 原子完成清理、检查和记录。拒绝请求不新增该维度的记录，也不延长该 key 的 TTL。三个维度逐项预占，后续维度拒绝时不回退之前的额度；这是保守计数，不是三个 key 的全局事务。单 key 脚本可避免 Redis Cluster 的跨槽问题。账号和 IP 只以 SHA-256 摘要进入 key，不直接写入日志或 Redis key 明文；摘要不等于加密。

## 本地启动

已有本机 PostgreSQL 时，仅启动 Redis 即可。在项目根目录运行：

~~~powershell
docker compose up -d --wait redis
~~~

全新容器环境可运行 docker compose up -d --wait postgres redis。Docker Desktop 需要处于运行状态。

.env.example 已增加 REDIS_HOST、REDIS_PORT、REDIS_PASSWORD。原有 .env 不自动覆盖；缺失时后端默认连接 127.0.0.1:6379、无密码。Compose 仅将 Redis 绑定到本机回环地址；若配置 REDIS_PASSWORD，Compose 与后端必须使用相同的值。生产使用系统/容器环境变量提供凭证。

后端以 backend 为工作目录启动，使用 JDK 21。两个进程可以分别在 8080、8082 启动；第二个终端设置 SERVER_PORT=8082、LOG_FILE=../data/logs/after-sales-agent-8082.log 后运行 mvn spring-boot:run。相同环境的两个实例必须使用同一数据库、同一套 Redis、相同 Session 命名空间和限流参数。无需配置粘性会话。已有浏览器的旧本地 Session 无法自动迁移，需要重新登录。

## 配置与故障行为

app.security.login-rate-limit 绑定 LoginRateLimitProperties，启动时校验额度及窗口均为正数。namespace 默认 after-sales:<app.environment>:login-limit；Session 使用 after-sales:<app.environment>:session。生产 app.environment=prod，测试与评测环境分别隔离。

Spring Boot 4 的 Session 属性为 spring.session.data.redis.*。Session 超时 30 分钟，Cookie 名称沿用 JSESSIONID。保留 HttpSessionSecurityContextRepository 和 HttpSessionCsrfTokenRepository，Spring Session 将底层 HttpSession 保存到 Redis。生产继续要求 HTTPS 和 Secure Cookie。

限流拒绝：HTTP 429、code=LOGIN_RATE_LIMITED，带 Cache-Control: no-store 和 Retry-After 秒数。Retry-After 表示本次被拒绝维度的最早重试时间；其他请求仍可能消耗额度。前端已有 429 提示。限流器访问 Redis 失败时拒绝进入认证，复用现有 AUTH_SERVICE_UNAVAILABLE/503；该异常在认证 try/catch 之前抛出，不清理已有登录会话。

整个 Redis 不可用也会影响共享 Session。RedisAvailabilityFilter 的注册顺序位于 Spring Session 之前，能够将会话读取、CSRF 校验、会话保存阶段的 Redis 连接/命令异常转换为统一 503；已提交的响应无法重写，会继续向外传播异常。一般数据库异常不会被标记为 Redis 故障。Redis 故障切换/数据淘汰可能丢失计数，不能将该方案视为跨故障的强一致配额。建议为 Session 和限流使用有容量监控的 Redis，避免主动淘汰有效数据。

账号全局额度可能被他人耗尽；按业务调整阈值，必要时转验证码或二次验证。共享出口 IP 较多的场景也应提高 IP 阈值。此实现保护进入 Controller 的合法登录尝试，入口还需保护 /csrf 和畸形请求的流量。

## 可信代理与 Nginx

默认 FORWARD_HEADERS_STRATEGY=none，后端不信任客户端直接提交的转发头。生产经 Nginx 接入时，配置系统/容器环境变量：

~~~text
FORWARD_HEADERS_STRATEGY=native
TRUSTED_PROXY_PATTERN=10[.]0[.]0[.]10
~~~

TRUSTED_PROXY_PATTERN 必须替换成后端实际看到的代理连接来源地址，默认 ^$ 不匹配任何代理。不要使用覆盖所有地址的表达式，也不要仅开启 native 而忽略可信代理配置。后端端口只允许可信代理访问。

下面示例仅适用于一层 Nginx 入口。upstream 放入 http 块，location 放入现有 HTTPS server 块：

~~~nginx
upstream after_sales_backend {
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
}

location /api/ {
    proxy_pass http://after_sales_backend;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Forwarded "";
}
~~~

Nginx 覆盖外部传入的转发头，Tomcat 仅在来源命中可信代理时还原 IP，LoginRateLimiter 只使用 request.getRemoteAddr()。多层负载均衡需要按实际可信链调整，不能直接照搬这个一层示例。Vite 开发代理通常让后端看到回环地址，不能用于验证真实客户端 IP 分流。

## 测试

普通测试无需 Redis/PostgreSQL：

~~~powershell
Set-Location backend
mvn test
~~~

RedisLoginIntegrationTest 默认跳过，显式指定测试 Redis 后执行。测试使用随机 UUID 命名空间，只删除自己创建的 key，不执行 FLUSHDB/FLUSHALL：

~~~powershell
$env:REDIS_TEST_HOST="127.0.0.1"
$env:REDIS_TEST_PORT="6379"
# Redis 配置了认证时，还需设置 REDIS_TEST_USERNAME / REDIS_TEST_PASSWORD
mvn '-Dtest=RedisLoginIntegrationTest' test
~~~

普通测试同时执行真实 SecurityFilterChain 和 SessionRepositoryFilter，覆盖缺失 CSRF 的 403、登录 Session ID 与 CSRF 轮换、退出失效，以及持有会话 Cookie 时会话存储故障返回 503；此处使用内存会话仓库。Redis 集成测试另外覆盖两个独立 Redis 连接下的并发额度共享、跨 IP 账号额度、窗口到期恢复，以及两个 SessionRepository 间的 SecurityContext、CSRF token 共享和注销。

完整浏览器联调：先通过实例 A 获取 /api/v1/auth/csrf，再携带同一个 Cookie 和 CSRF header 请求实例 B 的 /login，登录后刷新 CSRF，并通过 A 的 /me 确认身份；通过 B 退出后 A 的 /me 应返回 401。同一 IP＋账号在 300 秒内前五次进入认证，第六次即使密码正确也返回 429。认证失败会清理 Session，下一次尝试前需要重新获取 CSRF。
