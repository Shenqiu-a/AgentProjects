## 推荐开工顺序

1. 明确第 3 章的模拟业务规则，画出一个用户问题的执行过程。
2. 按第 13 章 S0、S1 完成环境、登录和订单查询，先验证普通后端接口。
3. 实现文档解析与检索，再接入真实模型进行带引用的回答。
4. 实现只读工具，随后加入售后草稿和用户确认。
5. 最后完善 SSE、恢复、评测和演示材料。

开发过程维护一份 `PROGRESS.md`：记录阶段、已完成接口、验证证据、遇到的问题和下一步。它是建议你在业务项目中创建的文件，本包没有伪造实现进度。

## 阅读约定

- 接口 ID（如 D04）与 OpenAPI 的 `operationId` 一致。
- 示例 UUID 只是契约示例；固定业务数据的编号与映射见主文档第 7 章。
- 示例指标是验收目标或演示值，不代表已经运行项目测得的结果。
- 售后规则属于本项目的虚构商店配置，不能当作真实商家的承诺或法律规则。
- `mock` 运行用于练习和自动化测试；`live` 运行才调用真实模型。界面必须显示实际调用记录。
- 主文档中的官方链接已于文档日期核对；具体依赖补丁版本在项目初始化时固定并记录。

## 接口契约的使用方式

将 `openapi.json` 导入支持 OpenAPI 3.1 的 Swagger Editor、Apifox 或类似工具，按模块生成调试请求。契约采用 Cookie 会话认证，写接口还要求 CSRF 请求头。首次调试应按“获取 CSRF → 登录 → 再获取 CSRF → 调用业务接口”的顺序。

OpenAPI 能描述字段结构和状态码；它不能替代业务状态机、事务边界和并发约束。实现时同时对照主文档。
